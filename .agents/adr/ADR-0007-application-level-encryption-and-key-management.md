# ADR-0007 — Application-Level Encryption and Key Management

> **Status:** Accepted  
> **Date:** 2026-07-20  
> **Decision Owners:** Security and Platform  
> **Technical Specification References:** Sections 10, 11, 17, 21, 22, 27, 29, and 30; `ADR-0005`; `ADR-0006`; `OD-009`  
> **Supersedes:** None  
> **Superseded By:** None

## Context

Socrato requires reversible application-level encryption for exceptionally sensitive values: Teacher-visible Student name payloads and recoverable Student Access Code representations. Database and storage encryption supplied by the hosting provider remains necessary but does not protect against broad database reads, exports, or a database-only disclosure.

The hosting and production key-management provider have not yet been selected. The cryptographic contract and hierarchy can nevertheless be fixed independently, while production enablement remains gated on a compliant managed KMS binding.

## Decision Drivers

- authenticated confidentiality and tamper detection;
- keys outside PostgreSQL and source control;
- environment and purpose separation;
- safe rotation without simultaneous full-database migration;
- compatibility with Node.js server runtimes and managed KMS services;
- algorithm agility and testability;
- recoverability without exposing keys to operators or browsers;
- deletion, backup, and incident-response support.

## Decision

### Approved Algorithm

Application field encryption MUST use:

```text
AES-256-GCM
```

Each encryption MUST use:

- a 256-bit Data Encryption Key;
- a unique 96-bit nonce generated by a cryptographically secure random source;
- a complete 128-bit authentication tag;
- authenticated additional data defined by the owning data contract;
- binary-safe encoding at the persistence boundary.

Authentication tags MUST NOT be truncated. Decryption MUST authenticate the ciphertext and additional data before returning any plaintext. Authentication failure MUST fail closed and MUST NOT return partial plaintext.

The implementation MUST use the maintained Node.js cryptographic API or a separately reviewed maintained library. Custom cryptographic primitives are prohibited.

### Envelope Key Hierarchy

The hierarchy is:

```text
Managed KMS Key Encryption Key (KEK), one per environment
  → wraps versioned purpose-specific Data Encryption Keys (DEKs)
      → DEK: student_name_payload
      → DEK: student_access_code_recovery
```

The KEK MUST:

- be generated or imported through an approved managed KMS;
- remain non-exportable where the provider supports it;
- be distinct for development, preview/test, staging, and production;
- permit unwrap/decrypt only to the approved server runtime identity;
- deny browser, analytics, general database, and ordinary human access;
- produce provider audit evidence for administrative key operations.

Purpose-specific DEKs MUST be random 256-bit keys. A DEK for Student names MUST NOT encrypt recoverable Student Access Codes, and vice versa.

### Key Registry

PostgreSQL MAY store a restricted key registry containing only:

- stable purpose identifier;
- DEK version;
- KMS-wrapped DEK;
- KEK reference or version;
- algorithm identifier;
- lifecycle state;
- creation, activation, retirement, and destruction metadata.

The registry MUST NOT contain an unwrapped DEK, KEK material, plaintext sensitive data, or secret-manager credentials. It resides in `private` or another equivalently restricted schema and is unavailable to browsers.

### Runtime Key Access

Only the reviewed server cryptography adapter and narrowly authorized migration/re-encryption worker MAY request DEK unwrap.

An unwrapped DEK MAY exist only in protected server-process memory. It MUST NOT be serialized, logged, included in errors, persisted to disk, placed in distributed cache, or returned to application callers. In-memory caching MAY reduce KMS calls but MUST be bounded and discarded when the process terminates or the key is retired.

Normal domain services call typed `encrypt` and `decrypt` operations by purpose. They MUST NOT receive raw key material.

### Encrypted Envelope Format

Every encrypted value MUST carry or resolve to:

```text
envelope_version
algorithm
purpose
dek_version
nonce
ciphertext
authentication_tag
```

Authenticated additional data MUST bind at minimum:

- application identifier;
- deployment environment;
- schema and entity type;
- stable record identifier;
- encrypted-field purpose;
- envelope and DEK versions.

AAD MUST be reconstructed deterministically and MUST NOT contain secret material. Binding prevents ciphertext from one record, field, purpose, or environment from being substituted into another.

### Nonce Safety

Every encryption, including updates and re-encryption, MUST generate a new 96-bit nonce. A nonce MUST never be reused with the same DEK.

The encryption adapter MUST centralize nonce generation. Callers MUST NOT supply nonces in production code. Tests MUST include forced-nonce and substitution failure cases. Key usage counters and rotation policy MUST keep encryption volume far below the approved AES-GCM safety bound.

### Key Rotation

Rotation uses versioned DEKs with:

- exactly one active write version per purpose and environment;
- bounded read support for active and retiring versions;
- new writes using only the active version;
- idempotent background re-encryption of older ciphertext;
- verification before replacing old ciphertext;
- measurable migration progress and failure reconciliation;
- retirement only after database and backup policy conditions are satisfied.

Routine DEK rotation SHOULD occur at least annually and MAY occur earlier for operational policy. Immediate rotation is REQUIRED after suspected key exposure, cryptographic implementation defect, unauthorized KMS access, or provider direction.

KEK rotation SHOULD use managed KMS rewrapping of DEKs without decrypting all application data. Rotation MUST be rehearsed outside production.

### Provider Binding

Production MUST NOT use a raw long-lived root encryption key stored only as a Vercel environment variable or PostgreSQL secret. It MUST bind the key-management adapter to an approved managed KMS or HSM-backed equivalent before encrypted Student data enters production.

Because the final hosting provider is not yet selected, the concrete KMS product and residency configuration remain an environment-readiness item. Selection MUST verify Canadian/Québec deployment requirements, availability, audit logs, IAM, backup recovery, cost, and incident procedures without changing this cryptographic contract.

Local development and automated tests MAY use a clearly marked local adapter with generated non-production keys held in ignored local environment configuration. Production data and production keys MUST never be copied into local or preview environments.

### Backup and Recovery

Database backup without the required KEK and wrapped DEKs is not a usable recovery. Recovery procedures MUST protect and test the complete dependency chain while keeping KEKs outside database backups.

At least one controlled recovery rehearsal MUST prove that authorized ciphertext can be decrypted in the restored environment and that deleted, expired, or revoked data is not reactivated. Key recovery access MUST be limited, documented, and audited.

### Deletion

Deleting a protected record MUST delete its ciphertext and cryptographic metadata under the applicable workflow. Purpose-level DEKs are shared and therefore MUST NOT be destroyed to represent deletion of one Student while other authorized records depend on them.

When a purpose DEK reaches the end of all required data and backup retention, destruction of the wrapped DEK and applicable KMS material MAY provide cryptographic erasure. Destruction requires verified dependency analysis and approval because it is irreversible.

### Operational Access and Incident Response

No developer, Teacher, Platform Administrator, support operator, or database operator receives routine raw-key access. Exceptional key administration requires named individual access, least privilege, MFA, approval, provider audit evidence, and an incident/change record.

On suspected compromise, the system MUST support:

- disabling decrypt operations by purpose;
- retiring the affected key version;
- activating a new write version;
- revoking affected credentials or Sessions;
- re-encrypting retained data;
- identifying affected records without logging plaintext;
- documenting notification and recovery decisions.

## Rejected Alternatives

- **Database-only encryption at rest:** insufficient against broad database access.
- **One shared application key for every field and environment:** unacceptable blast radius.
- **Deterministic encryption for name sorting:** leaks equality and is unnecessary.
- **AES-CBC without authenticated integrity:** vulnerable to undetected modification and misuse.
- **Keys stored beside ciphertext in PostgreSQL:** defeats the additional application boundary.
- **Custom encryption or hand-built key derivation:** excessive implementation risk.

## Consequences

### Positive

- database-only disclosure does not reveal protected values;
- tampering and record substitution are detected;
- purpose and environment isolation reduce compromise scope;
- versioning supports rotation and algorithm migration;
- the provider-specific KMS can be selected later without changing domain contracts.

### Negative

- production requires a managed KMS and operational expertise;
- decrypt operations introduce latency and availability dependency;
- key loss can make data permanently unrecoverable;
- rotation, backup, and incident procedures require continuous testing;
- KMS selection remains a production-readiness gate.

## Privacy Impact

Encryption reduces disclosure risk but does not authorize additional collection or retention. Data minimization, access control, AI exclusion, and deletion remain mandatory independently of encryption.

## Security Impact

The design protects confidentiality and integrity of selected fields against database-only compromise. It does not protect plaintext after authorized server decryption or a fully compromised application runtime; least privilege, session controls, monitoring, and minimal plaintext lifetime remain essential.

## Cost Impact

KMS operations and audit storage create a small recurring cost. Bounded in-memory DEK caching avoids one KMS call per roster field while preserving the external key boundary. Actual provider cost MUST be included in the production cost model.

## Validation

Tests and operational evidence MUST prove that:

1. AES-256-GCM uses 256-bit DEKs, unique 96-bit nonces, and 128-bit tags;
2. modified ciphertext, nonce, tag, AAD, record identifier, environment, or purpose fails closed;
3. keys are distinct across purposes and environments;
4. raw KEKs and DEKs never appear in PostgreSQL, source control, logs, errors, browser bundles, or analytics;
5. only approved runtime identities can unwrap DEKs;
6. rotation supports dual-read/single-write and idempotent re-encryption;
7. retired versions cannot encrypt new data;
8. backup recovery restores authorized access and reapplies deletion and revocation;
9. local and preview environments cannot decrypt production ciphertext;
10. KMS unavailability produces controlled failure without plaintext fallback;
11. key-administration actions generate provider and Socrato audit evidence;
12. incident exercises demonstrate purpose-level disablement and rotation.

## Reconsideration Triggers

Revisit this decision before changing the cipher or tag length, allowing callers to supply nonces, using deterministic encryption, adding high-volume protected fields near AES-GCM usage limits, changing KMS provider trust boundaries, enabling multi-region writes, introducing client-side decryption, or adopting hardware-backed requirements that the selected KMS cannot meet.

This ADR resolves `OD-009`. Production remains blocked until a compliant managed KMS provider, region, IAM policy, and recovery procedure are configured and verified.
